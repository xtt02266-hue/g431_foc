## 1. 这次解决的复杂度

原工程已经按职责拆分目录，但函数内部仍有三个主要问题：协议处理同时承担多类业务；1 ms 任务交织反馈、心跳、标定和模式控制；标定状态机把输入检查、阶段推进、统计和结束处理集中在一个函数。

本次以清晰的业务步骤组织这些流程。主函数负责决定执行顺序和提前返回，辅助函数完成一项业务。辅助函数优先留在原文件，避免为了拆分而增加目录层级、通用框架或函数指针注册表。

## 2. 辨识 STOP 修复

### 2.1 原问题的代码依据

原停止入口会取消普通标定、撤销运行请求、复位控制历史和禁用电流环，但没有取消电机参数辨识。

TIM2 首先调用参数辨识任务；状态更新遇到参数忙碌会优先进入辨识状态。辨识开环函数直接写 TIM1 比较寄存器，因此后续辨识步骤可能覆盖之前的零输出。SVPWM 的软件禁用标记不能约束这个直接写寄存器的路径。

这是源码中可达路径的判断。本次模拟验证补充了回归检查，尚未通过真实电机复现或验收。

### 2.2 取消接口与执行顺序

新增接口：

```c
void motor_identify_cancel(void);
void motor_parameters_cancel_identification(void);
```

底层辨识取消负责撤销开环输出、结束状态机和清理计时、角度及采样累积。参数模块取消负责停止本次会话、清除自动辨识待触发标志、恢复参数就绪状态。

统一停机在原临界区内先取消参数辨识，再取消普通标定、撤销运行和输出，最后恢复普通标定的配置。取消不会在中断中读取或擦写 Flash。

协议 STOP 原本先调用停止入口，再调用会再次停止的主机释放入口。本次保留一次主机释放调用；停机、清目标、控制权释放和协议令牌清理仍然发生。

### 2.3 参数恢复规则

| 情况 | 取消后的结果 |
|---|---|
| 通过参数模块启动，之前存在有效参数 | 从 RAM 副本恢复参数，保持停机 |
| 之前没有有效参数 | 回到 `NO_DATA`，不自动重新辨识 |
| 结果待保存，后台尚未领取候选结果 | 丢弃本次候选结果 |
| 后台已经领取候选结果并进入保存流程 | 允许前台保存流程结束；旧会话不得覆盖取消后的就绪状态 |
| 传感器异常导致辨识失败 | 保持错误状态，不当作正常取消 |
| 旧调试调用直接启动底层辨识 | STOP 同样取消；因没有参数模块保存的会话副本，撤销参数就绪状态 |

辨识开始会清空当前结果，因此恢复一个 `READY` 标志不足以恢复正常运行。参数模块在开始前保存有效参数本身，以及此前就绪和存储标志；取消时通过已有参数应用入口恢复。

恢复入口继续使用当前配置中的标称 R/L 和极对数，恢复安装相关的方向和零角。传感器异常后需重新完成辨识和正常启动检查，不能用取消操作清除错误。

### 2.4 后台保存与取消交错

参数会话增加版本计数。后台在原中断状态保护下领取候选参数和版本，然后在前台完成 Flash 保存；结束时再次检查版本和状态。

如果期间发生取消，后台不再把旧会话发布为 READY 或 ERROR，也不恢复运行请求。存储标志反映此次保存返回结果，RAM 中恢复的旧参数继续用于后续显式启动。

取消无法撤回已经启动的 Flash 擦写。已经被后台领取的候选结果可能落入 Flash，下次上电仍会走原有 Flash 加载流程。这次没有修改 Flash 记录格式或引入双页事务存储。

### 2.5 每次辨识步骤前的传感器保护

启动和每次活动辨识步骤都检查编码器样本年龄，沿用 2 ms 门限。检查放在实际辨识任务入口，覆盖直接调用任务的路径；失效后撤销开环输出并进入错误状态。

协议辨识统一调用应用层启动入口，应用层负责与其他标定任务互斥、接受请求和运行请求处理。接受辨识后清除正常运行请求；完成辨识和保存后仍需显式 START，避免旧请求恢复转矩。

私有函数 `identify_measure_r/l()` 改名为装载标称电阻、电感的函数，公开状态枚举数值保持兼容。保留原有等待时间。

## 3. 1 ms 任务怎样变得更清楚

目前主流程为：

```c
void motor_control_task(void)
{
    motor_runtime_feedback_t feedback;
    motor_runtime_update_feedback(&feedback);
    motor_runtime_check_host_timeout();
    if (motor_runtime_step_calibration(&feedback)) {
        return;
    }
    if (motor_runtime_handle_force_drag()) {
        return;
    }
    float target_pos = motor_system_update_pot_target();
    g_foc_state.target_d = 0.0f;
    motor_cogging_task1ms((g_motor_system.state == MOTOR_STATE_SENSORED_RUN) &&
                          ((g_control_mode == MOTOR_CONTROL_SPEED) || (g_control_mode == MOTOR_CONTROL_FREE)));
    if (motor_runtime_handle_music()) {
        return;
    }
    motor_runtime_run_control_mode(&feedback, target_pos);
}
```

返回值为 `uint8_t` 的三个阶段处理函数统一约定：返回 1 表示本周期已经处理完毕，调用者应立即返回。

### 3.1 各步骤的职责

| 步骤 | 负责内容 |
|---|---|
| 反馈更新 | 原有速度估计、方向转换和机械角度解回绕 |
| 心跳检查 | 原超时计算及主机控制权释放 |
| 标定推进 | 状态检查、点位/旋转推进、目标变化时 PI 复位、结束停机和配置恢复 |
| 强拖 | 对齐等待、速度斜坡、相位推进和开环幅值 |
| 音乐 | 原自动播放条件、进入/退出时的带宽与历史处理、播放任务 |
| 正常模式 | 力矩、速度、点位标定、触觉和普通位置模式的原优先级 |
| 标定采样发布 | 控制结果、传感器质量字段及原临界区 |

### 3.2 保留的时序关系

反馈更新先于心跳检查；标定先于强拖；强拖提前返回不会额外读取电位器；音乐处理仍在普通模式前；标定采样仍在对应控制输出计算之后发布。

点位标定保留原模式覆盖条件。非运行分支保留每周期复位控制历史的行为，这次没有改成只在状态进入时复位。

反馈结构只包含已经读取的局部值：控制方向速度、原始角计数和方向。它不是跨中断一致快照，也没有把原有多个时间点的读取合并成一次新采样。

## 4. 协议处理怎样拆分

`handle_command()` 保留请求解析、请求重放、权限与校准门控、统一回复和请求缓存。通过门控后的命令按领域分派给同文件内的静态函数。

| 领域 | 内容 |
|---|---|
| 连接与控制权 | HELLO、状态查询、CLAIM、STOP、CLEAR_FAULT |
| 标定管理 | 标定信息、启动、取消、状态及编码器校准启动 |
| 标定历史回放 | 会话匹配、历史记录读取和编码 |
| 启停与辨识 | START、IDENTIFY、RELEASE、心跳和强拖 |
| 主机目标 | 模式、Iq、限幅和速度目标 |
| 模型配置 | 触觉、摩擦、速度 PI、齿槽补偿配置 |
| 齿槽表事务 | 开始、分块写入、提交、读取和保存 |

回复缓冲区仍由主函数提供，各处理函数写回复内容和长度。没有为每个领域复制大缓冲区。

### 4.1 为什么保留校验顺序

一个请求可能同时存在长度错误、控制权错误和设备忙碌。如果任意调整检查顺序，上位机收到的错误码可能改变。

本次保留原来的无令牌命令处理、令牌校验和校准门控优先级，以及每个命令的长度与数值检查顺序。安全修复导致的辨识接受条件变化单独测试。

### 4.2 共用标定批次编码

新增同文件静态编码函数 `build_calibration_batch()`，统一：

- 12 字节批头。
- 普通 64 字节记录。
- 点位 68 字节记录，包括目标位置。
- 会话、丢样数量、模式 schema 和记录条数。

实时发送仍从队列 peek，在成功进入发送队列后才 consume。回放仍读取历史记录，不推进消费位置。编码函数不决定发送优先级或消费行为。

增加样本结构 64 字节的编译期断言，防止结构布局变化悄悄破坏协议。

## 5. 标定状态机的职责边界

### 5.1 旋转标定

主函数依次检查采样有效性、更新角度增量、处理归零、检查停转，再分派稳定或采集阶段。

归零函数负责方向、速度档和通过数量的推进；稳定函数保留摩擦与齿槽各自的窗口和门限；采集函数保留每圈均值、RMS、峰值、有效圈数和超时。

没有改变 5 秒/5 圈起始条件、连续稳定窗口、采集圈数、停转判断和失败原因。

### 5.2 点位标定

最短机械误差计算、采集窗口判断、下一点/方向/轮次推进和连续稳定窗口各自封装。

主函数保留辅助撤销后的提前返回、质量失败后的重试、完成会话时的返回，以及最后的辅助重新进入和超时检查。

采集失败仍要求新的有效窗口，覆盖的历史记录仍无法回放；不会插值、补造或隐藏缺失数据。

### 5.3 编码器芯片自校准

后台先处理清理和公共保护，再按 RAMP、SETTLE、CONFIGURE、RUNNING 分派。

SPI 配置步骤保留忙碌/成功/失败三种结果、频率读回和保留位处理、触发前的重新上电标志，以及触发事务期间被 STOP 打断后的状态检查。

成功仍要求观察到运行状态及足够的累计机械运动；过期成功结果不作为本次成功。清理与必须重新上电的规则保持原有行为。

### 5.4 标定会话启动

启动检查放在 `calibration_session_validate()`；配置保存和配置应用各自封装。会话建立、保存配置和运行请求仍在原临界区内完成。

配置恢复仍由既有统一停止路径执行，包括摩擦、齿槽、限幅、模式、输入来源和位置 PI 输出范围。

### 7.3 顺带修正的旧测试问题

原点位边界测试硬编码“3 个计数可接受”，而修改前与当前配置门限都已经是 2 个计数。边界用例现在使用 `MOTOR_CAL_POINT_MAX_ERROR_COUNTS`，测试允许门限和超出一计数，以及跨零点边界。固件保护门限没有改变。

平均策略的旧断言要求单次位置超差立即拒绝，而基线已按整窗平均绝对误差判断。测试增加“一次短暂偏差随后回到目标”与“整窗超差”两个情形，并保留电流跟踪失败和传感器异常检查。修正后的策略断言在修改前安全基线与当前代码上都通过。

原编码器测试存在同一行 for 后接 assert 的误导缩进，补充花括号后继续进行 `-Werror` 检查。

完整标定测试保留数百万个模拟周期，没有缩短稳定或采集窗口。最终全部 C 断言通过。

`run_checks.py` 需要本机已保存的安全修复快照。`--capture` 只用于在安全修复完成、结构调整开始之前建立快照；不要在当前重构后代码上重新捕获并称为修改前基线。

测试 ELF 会强制保留部分正常链接时被裁剪的入口，资源数值不代表实际固件；`--production` 使用正常链接配置。

所有源码快照、构建产物、生成的 JSON、链接脚本、测试副本和日志均留在 `.codex_tmp`。版本库只新增必要的验证脚本和本文。

## 9. 后续维护方式

新增模式先放在对应业务模块，由运行主函数分派。新增协议命令先判断所属领域，再在该处理函数中补充长度和数据检查，维持外层权限顺序。

新增共享变量前先明确由谁写入、谁读取、在哪个执行上下文访问；仅单模块使用的历史变量优先保持静态。新增复位操作先明确是观测清零、控制历史复位还是安全停机。

对连续数学算法，优先保留计算顺序并补充单位和符号说明。对混合业务流程，优先提取完整业务步骤。超过约 80 行时检查职责，但不把行数作为硬性要求。
